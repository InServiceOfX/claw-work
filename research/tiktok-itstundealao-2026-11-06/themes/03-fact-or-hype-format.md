# "Fact or Hype?" format pattern

Structural analysis of the recurring video format used by @itstundealao since approximately July 2026. This documents the format as a repeatable content structure — it does not claim causation for engagement metrics.

## Format structure

1. **Hook**: Title card or spoken hook ("Fact or Hype?") + a bold claim about an AI tool
2. **GitHub screen**: Show the repository page (establishes credibility/source)
3. **Install via agent**: Install the tool using a coding agent (Claude Code, Cursor, etc.)
4. **Live test**: Run the tool on a real project/task
5. **Cost display**: Show the token/API cost from the session
6. **Verdict**: On-screen checkbox (✅ FACT or ❌ HYPE)

## Observations

### View correlation (not causation)

Videos using this format often show 0.2–1.6M views in the creator's catalog. Earlier tip/comparison videos often show 5–20K views.

**This is correlation only.** Possible confounds:
- Timing (algorithm changes, audience growth)
- Topic selection (more viral-ready tools in recent videos)
- Platform trends (short-form coding content growing overall)
- Creator's growing follower base

The format did not necessarily cause the growth.

### Cost transparency

The on-screen cost display (e.g., "$6.17 / ~61k output tokens") gives viewers a concrete expectation. This counters vague "AI is expensive" or "AI is free" claims.

However: costs shown are single-run anecdotes, not representative benchmarks. They depend on model choice, prompt length, and task complexity.

### Source accountability

Showing the GitHub repo screen:
- Establishes the tool exists (not vaporware)
- Shows stars/activity as social proof
- Enables viewers to verify claims independently

This is more accountable than link-in-bio or "DM for code" patterns.

### Verdict framing

The binary FACT/HYPE verdict:
- Creates a clear takeaway (memorable)
- Risks oversimplification (nuanced tools get compressed to one bit)
- Encourages engagement (viewers may disagree)

## Reusable elements (general pattern)

For any tool/claim review format:

1. **Testable claim in hook** — not just "I tried X" but "X claims to do Y"
2. **Show source** — URL visible, not just named
3. **Live demo, not staged cut** — real install, real errors
4. **Quantifiable output** — cost, time, tokens, accuracy
5. **Clear verdict** — even if simplified

## What this format does not do

- Deep technical review (surface-level testing)
- Benchmark comparisons (one tool, one run)
- License/security audit (out of scope for 60s)
- Long-term reliability assessment

The format works for discovery/triage, not due diligence.

## Excluded from adaptation

The creator uses a personal-brand/on-camera style. This research documents the structural elements, not the persona. No recommendation to replicate personal presentation style.
